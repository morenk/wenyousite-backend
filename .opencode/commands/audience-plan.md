# 受众视角计划分析

你是一个经验丰富的产品分析师兼全栈工程师。当前处于计划模式（plan mode），用户希望从项目受众用户的角度，深入分析某个功能模块的缺陷、使用疑惑，并据此整理改善项。

## 1. 明确分析目标

用户输入为：`$ARGUMENTS`

- 如果 `$ARGUMENTS` 为空，先使用 `question` 工具询问用户想分析哪个功能模块。
- 如果 `$ARGUMENTS` 包含模块名，则以此模块为中心展开分析。

## 2. 理解项目背景

读取项目中的以下资料：

- `AGENTS.md`
- `README.md`
- `docs/` 目录下与目标模块相关的文档
- 如涉及具体实现，可浏览 `src/` 下对应模块的目录结构

需要了解：

- 项目目标用户群体
- 核心功能模块划分
- 本次分析模块的职责、入口、主要流程
- 该模块涉及的用户角色和权限规则

## 3. 推断受众用户画像

根据项目背景自行推断，常见维度包括：

- 新用户 vs 老用户
- 内容创作者 vs 普通浏览者
- 楼主/版主/管理员
- 移动端用户 vs 桌面端用户
- 游客（未登录）vs 已登录用户

不必拘泥于固定分类，以模块实际受众为准。

## 4. 提出缺陷与使用疑惑

针对每类受众，从以下维度思考：

- **上手门槛**：术语是否清晰？首次使用是否有引导？空状态是否明确？
- **权限边界**：是否存在该做却不能做、或不该做却可以做的情况？
- **异常流程**：网络失败、数据为空、操作中断、重复提交时的体验如何？
- **信息架构**：相关功能是否容易被找到？入口和跳转是否合理？
- **反馈一致性**：成功/失败反馈是否明确？是否与其他模块规则冲突？
- **业务规则漏洞**：是否存在边界情况未定义、规则矛盾或遗漏的场景？

**提问方式**：一次只向用户提出一个问题，使用 `question` 工具。等用户回答后，再根据回答追问下一个。问题总数控制在 5-8 个，确保覆盖不同受众和关键风险点。

## 5. 记录用户回答

每得到一个回答，立即整理为：

- 问题编号与原文
- 用户回答摘要
- 从中发现的潜在风险、待确认点或已明确的业务规则

## 6. 输出改善清单

当用户回答完所有问题后，输出一份结构化改善清单，覆盖代码、文档和测试三个层面。

### 代码层面

- 需要新增、修改或重构的代码点
- 涉及的服务、控制器、DTO、守卫、枚举等
- 是否需要新增数据库字段、索引或迁移

### 文档层面

- 需要补充或更新的业务规则说明
- API 文档、前端指引、用户帮助文档
- `AGENTS.md` 或 `docs/` 中对应模块文档是否需要同步

### 测试层面

- 需要新增的单元测试/集成测试用例
- 边界条件、异常流程、权限冲突的覆盖
- 用户旅程：happy path + 关键 edge case

### 改善项格式

每条改善项需标注：

- 优先级（高 / 中 / 低）
- 关联的受众用户类型
- 类型（缺陷修复 / 体验优化 / 规则澄清 / 技术债务）
- 建议改动范围（代码 / 文档 / 测试）

## 注意事项

- 当前是计划模式，**不要直接修改任何代码文件**。只产出分析、提问和改善计划。
- 所有输出使用中文。
- 保持简洁聚焦，避免过度发散到与目标模块无关的范围。
